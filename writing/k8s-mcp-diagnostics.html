Autonomous Kubernetes Diagnostics via Read-Only MCP

By Akkireddy Challa / 1 November 2026 / 3 min read

#Kubernetes #MCP #Observability #Platform engineering

Giving autonomous AI agents raw shell access or direct kubectl privileges inside production clusters creates unacceptable security exposure. Prompt injection can trigger accidental namespace deletion or privileged secret exfiltration. Packaging cluster diagnostics into a bounded, strictly read-only Model Context Protocol server creates a safe operational bridge between AI agents and the Kubernetes control plane.

Architecting the read-only FastMCP boundary

Our server implementation relies on FastMCP communicating over stdio JSON-RPC. The client initialization layer implements an automated fallback: it attempts in-cluster configuration first for containerized pods, falling back to local kubeconfig files during workstation development. Crucially, the service account binds only to non-mutating verbs on core and networking API groups, completely withholding write permissions and restricting access to Secret resources.

Detecting abnormal pod lifecycle transitions

Raw Kubernetes pod manifests contain verbose configurations that quickly overwhelm an agent's context window. Instead of dumping raw JSON, the diagnostic tool iterates through container statuses, evaluating waiting reasons and terminated exit codes. It surfaces a synthesized boolean flag indicating abnormal state, highlighting CrashLoopBackOff, ImagePullBackOff, and OOMKilled events alongside restart counts and pod IPs.

Triage with previous container logs

When containers restart in a crash loop, querying current pod stdout often returns only initial startup messages. By exposing a bounded tail parameter between 10 and 500 lines and capturing logs with the previous instance flag enabled, agents can immediately inspect the fatal stack trace from the crashed process without human operator intervention.

Efficient warning event aggregation

Querying cluster events without filtering can flood memory with routine informational messages. The server pushes event filtering upstream to the API server using field selectors focused solely on warning events. This surfaces FailedScheduling, FailedMount, and BackOff occurrences with deduplicated event counts, timestamps, and target resource references.

Conclusion

Bounded MCP servers turn AI assistants into reliable, safe first-responders for Kubernetes platform teams. By enforcing read-only RBAC, condensing pod health signals, and isolating crash logs, platform engineers can automate incident triage without granting unrestricted cluster access.
